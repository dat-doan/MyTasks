01 · BẮT ĐẦUBạn sẽ làm được gì sau tài liệu này

Expo Router cho phép dùng cấu trúc file để khai báo các màn hình và địa chỉ của chúng. Khi người dùng bấm một liên kết hoặc mở một deep link, Router tìm route phù hợp, đặt màn hình vào navigator và phối hợp với React Native để hiển thị giao diện.

Sau bài thực hành, bạn sẽ có app gồm danh sách công việc, hai tab, màn hình chi tiết theo ID và form tạo công việc dạng modal. Bạn sẽ hiểu vì sao tab bar biến mất ở detail, vì sao Back từ detail không quay lại form đã lưu, và dữ liệu được chia sẻ giữa các màn hình bằng cách nào.

Muốn chạy được ngay

Đi tới bài thực hành, tải ZIP, chạy mẫu trong thư mục riêng rồi đọc từng file theo hướng dẫn. Sau đó quay lại phần Stack và params để giải thích những gì vừa thấy.

Kiến thức cần có: biết component, props, state và thao tác cơ bản với TypeScript. Chưa cần tự cấu hình React Navigation. Ví dụ dùng JavaScript Tabs và native Stack ổn định; những API experimental mới hơn SDK 57 không nằm trong bài thực hành.

Phạm vi dữ liệu: lab lưu công việc trong bộ nhớ bằng React Context. Nó chưa có backend, đăng nhập thật hay lưu trữ bền vững. Điều này giúp quan sát luồng điều hướng và dữ liệu trước khi thêm các lớp khác.

02 · NỀN TẢNGTách file route URL và navigator

Ba khái niệm cần phân biệt ngay từ đầu là file route, URL và navigator. File nói màn hình nào tồn tại. URL xác định màn hình cần mở cùng các tham số. Navigator quyết định màn hình nằm ở đâu, có header hay tab bar không và Back sẽ đi về đâu.

Ví dụ file tasks/[id].tsx là một mẫu route. URL /tasks/1 chọn một công việc cụ thể. Nếu file đó thuộc root Stack, màn hình mở trên toàn bộ Tabs; nếu nó thuộc Stack bên trong một tab, quan hệ hiển thị sẽ khác.

Từ lệnh npm tới màn hình

Trong project hiện tại, npm run ios chạy expo start --ios. Expo CLI và Metro chạy trên Mac; Expo Go mở trong Simulator, lấy manifest và bundle, rồi thực thi JavaScript. Entry expo-router/entry đăng ký App của Router. Router xây cây route từ context module do Metro tạo và đưa layout, screen của bạn vào cây React.

Ở đây có hai thứ tự khác nhau. Nạp module là chạy code ở cấp file, gồm imports và khởi tạo object style. Render component là React gọi hàm component để lấy elements. Router có thể nạp một screen khi thu thập route trước lúc layout được render. Vì vậy không nên suy ra thứ tự evaluate file chỉ từ quan hệ cha con của component.

Router quản lý điều hướng còn dữ liệu thuộc ứng dụng

Mở /tasks/1 không tự tạo request lấy task 1. Screen phải đọc ID rồi lấy dữ liệu từ Context, store hoặc API mà ứng dụng chọn. Nếu ID hợp lệ về route nhưng không tồn tại trong dữ liệu, screen cần hiển thị trạng thái không tìm thấy tài nguyên.

03 · TỪ PROJECT CỦA BẠNĐọc được một app Router tối thiểu

Ở thời điểm bắt đầu soạn tài liệu, ví dụ khởi đầu trong project my-tasks có root layout trả về Stack, màn hình index render Greeting và file Greeting nằm dưới src/app/components. Phần này giữ ví dụ khởi đầu đó để nhìn rõ vai trò từng lớp, kể cả khi bạn đã tiếp tục thay đổi màn hình trong lúc đọc.

Layout gốc tối thiểu
import { Stack } from 'expo-router';

export default function RootLayout() {
  return <Stack />;
}

RootLayout không cần gọi Index() thủ công. Router phát hiện screen từ các file rồi gắn chúng vào Stack. Trong layout, Stack.Screen chủ yếu dùng để cấu hình tên hiển thị, header hoặc presentation của một route đã được phát hiện.

Điểm cần chỉnh khi tiếp tục project

File src/app/components/Greeting.tsx bị hiểu là một route có URL /components/Greeting. Component này nhận prop name từ màn hình, nên khi bị mở trực tiếp như route nó cũng không nhận dữ liệu theo cách màn hình index truyền vào.

Để sửa cấu trúc, chuyển component sang src/components/Greeting.tsx, rồi cập nhật import trong src/app/index.tsx thành ../components/Greeting. Hai đoạn dưới là phiên bản sau khi chuyển. Tài liệu chỉ hướng dẫn thao tác, chưa di chuyển file trong app hiện tại.

Muốn giữ tab bar khi mở chi tiết

Trong lab, detail tasks/[id].tsx nằm ngoài (tabs), nên root Stack mở detail ở phía trên cả Tabs. Tab bar không thuộc màn hình detail này. Muốn detail nằm trong vùng tab, tạo Stack trong tab Công việc rồi đặt cả index và detail dưới Stack đó.

Việc đặt navigator là một quyết định về trải nghiệm. Trước khi thêm file, tự hỏi: màn hình này thuộc khu vực nào, có cần giữ tab bar không, và Back nên quay về màn hình nào?

Vì sao xuất hiện hai header

Nếu root Stack hiện header cho screen (tabs), còn navigator con cũng hiện header, bạn có thể thấy hai thanh tiêu đề. Lab đặt headerShown: false ở screen (tabs) của root và để Tabs quản lý header bên trong.

06 · HISTORYHiểu push replace và back bằng stack

Đường dẫn hiện tại không mô tả toàn bộ lịch sử điều hướng. Hai người cùng nhìn màn hình /tasks/42 có thể có lịch sử Back khác nhau: một người đi từ danh sách, người kia mở thẳng deep link. Khi xử lý Back, hãy nghĩ tới state của navigator thay vì chỉ nghĩ tới URL.

07 · DỮ LIỆU TRONG URLTruyền ID và đọc dữ liệu đúng chỗ

URL có hai phần dữ liệu thường dùng. Path params điền vào segment động như [id]. Query params đứng sau dấu hỏi và mang thêm ngữ cảnh, chẳng hạn nguồn truy cập, từ khóa hoặc bộ lọc.

Với /tasks/42?source=home, route khớp file tasks/[id].tsx, id là chuỗi "42" và source là chuỗi "home". Trong lab, dữ liệu seed có ID 1 và 2; số 42 trong hình chỉ dùng minh hoạ cách phân tích URL.

Đọc và kiểm tra path params cùng query params
import { useLocalSearchParams } from 'expo-router';
import { Text, View } from 'react-native';

export default function ParamsDemo() {
  const params = useLocalSearchParams<{
    id?: string | string[];
    source?: string | string[];
  }>();
  const id = typeof params.id === 'string' ? params.id : undefined;
  const source = typeof params.source === 'string' ? params.source : undefined;

  // Chỉ chuyển số khi dữ liệu ứng dụng thật sự dùng ID số.
  const numericId = id && /^\d+$/.test(id) ? Number(id) : undefined;
  const isValidNumber = numericId !== undefined && Number.isSafeInteger(numericId);

  return (
    <View style={{ padding: 24, gap: 12 }}>
      <Text>ID gốc: {id ?? 'thiếu hoặc sai dạng'}</Text>
      <Text>Nguồn: {source ?? 'không truyền'}</Text>
      <Text>ID số hợp lệ: {String(isValidNumber)}</Text>
    </View>
  );
}

Generic TypeScript mô tả hình dạng bạn mong đợi, không kiểm tra URL từ bên ngoài. Hãy chuẩn hóa giá trị, xử lý thiếu tham số và kiểm tra quy tắc ID của ứng dụng. Với catch all [...parts], dữ liệu là mảng segment; khi cho phép query lặp, cũng nên xử lý dạng mảng.

Local params và global params

Một stack có thể giữ nhiều screen đã mount. Khi task 42 nằm dưới task 7, useLocalSearchParams của screen cũ vẫn mô tả route instance task 42; useGlobalSearchParams đi theo URL đang được chọn. Screen cần dữ liệu riêng của nó thường dùng local params. Global params hữu ích khi quan sát điều hướng ở phạm vi toàn app nhưng có thể làm các screen nền cập nhật không cần thiết.

Đổi bộ lọc của route hiện tại
import { router } from 'expo-router';

// Gọi từ onPress. Query thay đổi mà không thêm screen vào history.
export function showCompletedTasks() {
  router.setParams({ filter: 'done' });
}
// Ví dụ URL hiện tại sau khi gọi: /tasks?filter=done

Giữ URL gọn: truyền ID hoặc giá trị lọc ngắn rồi lấy object đầy đủ từ dữ liệu ứng dụng. Không đưa token, mật khẩu hay toàn bộ object task vào URL. Các tên screen, params, initial và state là reserved keys; tránh dùng làm query key nghiệp vụ.

Đối chiếu: URL parameters và phần API trong Router SDK 57. Quy tắc chuẩn hóa ID và giới hạn dữ liệu URL là lựa chọn thiết kế của các ví dụ trong tài liệu.

08 · STATE VÀ FOCUSMàn hình bị che có thể vẫn đang mounted

import { createContext, useContext, useRef, useState, type ReactNode } from 'react';

export type Task = {
  id: string;
  title: string;
  notes: string;
  completed: boolean;
};

type TasksState = {
  tasks: Task[];
  addTask: (title: string, notes: string) => string;
  toggleTask: (id: string) => void;
};

const initialTasks: Task[] = [
  { id: '1', title: 'Hiểu _layout.tsx', notes: 'Layout tổ chức navigator và provider.', completed: false },
  { id: '2', title: 'Mở một dynamic route', notes: 'ID thuộc URL; dữ liệu được đọc từ Context.', completed: true },
];

const TasksContext = createContext<TasksState | null>(null);

export function TasksProvider({ children }: { children: ReactNode }) {
  const [tasks, setTasks] = useState<Task[]>(initialTasks);
  const nextId = useRef(3);

  function addTask(title: string, notes: string) {
    const id = String(nextId.current++);
    const task: Task = { id, title: title.trim(), notes: notes.trim(), completed: false };
    setTasks((current) => [task, ...current]);
    return id;
  }

  function toggleTask(id: string) {
    setTasks((current) => current.map((task) =>
      task.id === id ? { ...task, completed: !task.completed } : task,
    ));
  }

  return (
    <TasksContext.Provider value={{ tasks, addTask, toggleTask }}>
      {children}
    </TasksContext.Provider>
  );
}

export function useTasks() {
  const context = useContext(TasksContext);
  if (!context) throw new Error('useTasks phải nằm trong TasksProvider.');
  return context;
}

Quan sát: ID được lưu dạng chuỗi để phù hợp cách dùng URL. Đây là chiến lược ID đơn giản của lab, không phải cách sinh ID dành cho dữ liệu đồng bộ nhiều thiết bị.

12 · KIẾN TRÚC NÂNG CAOBảo vệ nhánh route sau khi có session

Khi thêm đăng nhập, hãy tách ba trạng thái: đang khôi phục session, chưa đăng nhập và đã đăng nhập. Nếu chưa biết session mà đã render nhánh ứng dụng hoặc chuyển route vội, người dùng có thể thấy màn hình nhấp nháy hoặc gặp một chuỗi redirect khó dự đoán.

Stack.Protected cho phép mô tả những screen được truy cập khi một guard đúng. Khi guard chuyển sang false, các history entries của nhánh không còn được phép sẽ bị loại bỏ và Router chọn đích hợp lệ theo cấu hình.

Pattern bảo vệ route ở layout sau khi đã có SessionProvider
import { Stack } from 'expo-router';
import { Text } from 'react-native';
import { useSession } from '../contexts/SessionContext';

// Pattern nâng cao: useSession phải được triển khai và Provider đặt phía trên.
// Thêm file sign-in.tsx trước khi dùng cấu hình này.
export function RootNavigator() {
  const { session, isLoading } = useSession();

  if (isLoading) return <Text>Đang kiểm tra phiên đăng nhập…</Text>;

  return (
    <Stack>
      <Stack.Protected guard={!session}>
        <Stack.Screen name="sign-in" options={{ title: 'Đăng nhập' }} />
      </Stack.Protected>
      <Stack.Protected guard={!!session}>
        <Stack.Screen name="(tabs)" options={{ headerShown: false }} />
        <Stack.Screen name="tasks/[id]" />
        <Stack.Screen name="tasks/new" options={{ presentation: 'modal' }} />
      </Stack.Protected>
    </Stack>
  );
}

Đây là pattern kiến trúc, chưa nằm trong project ZIP. Trước khi dùng, bạn cần triển khai SessionContext, đặt SessionProvider phía trên RootNavigator và thêm screen sign-in.tsx. Nếu tích hợp vào lab, giữ TasksProvider ở ngoài navigator như hiện tại; redirect index đã nằm trong nhóm Tabs nên không khai báo root index nữa.

Luồng đăng nhập nên có trách nhiệm rõ

  1. SessionProvider khôi phục trạng thái xác thực từ giải pháp của ứng dụng.
  2. Trong lúc chờ, hiển thị loading hoặc phối hợp splash; chưa quyết định nhánh đăng nhập.
  3. Khi có kết quả, guard cho phép sign in hoặc nhánh ứng dụng.
  4. Đăng nhập thành công cập nhật session. Guard đổi và Router chọn nhánh được phép.
  5. Đăng xuất làm session không còn hợp lệ; history của các screen bị bảo vệ được xử lý theo guard.

Protected routes kiểm soát giao diện phía client. Server vẫn phải kiểm tra token, quyền truy cập và ownership của từng task. Một URL có ID đúng không chứng minh người dùng được phép đọc dữ liệu đó.

Để tránh loop, không đặt một redirect không điều kiện ở screen vẫn được phép truy cập sau khi session đổi. Hãy thử cả cold start, mở deep link khi chưa đăng nhập, đăng nhập, đăng xuất và nhấn Back.

Thêm route chỉnh sửa theo URL /tasks/1/edit. Đọc ID, tìm task, hiển thị form, bổ sung hàm update vào TasksContext rồi chọn hành vi sau lưu. Giữ scope task ở root provider.

Gợi ý route chỉnh sửa ở bài tập nâng cao
src/app/tasks/[id]/edit.tsx  →  /tasks/1/edit

router.push({
  pathname: '/tasks/[id]/edit',
  params: { id: task.id },
});

// Giữ [id].tsx hiện có cho /tasks/1.
// edit.tsx và màn hình detail dùng cùng TasksContext.
Câu hỏi để tự kiểm tra lời giải

URL thiếu hoặc sai ID có giao diện phù hợp chưa? Lưu xong có muốn quay lại form khi Back không? Nội dung task có cập nhật ở list và detail không? Deep link trực tiếp tới edit có hoạt động với task seed không?

Bài 4 Giữ tab bar khi mở detail

Thiết kế lại nhánh Công việc thành một Stack bên trong tab. Đặt list và detail dưới nhánh đó. Trước khi di chuyển file, vẽ lại cây navigator và liệt kê các href/name phải đổi.

Xem hướng giải

Có thể dùng (tabs)/tasks/_layout.tsx trả về Stack, (tabs)/tasks/index.tsx và (tabs)/tasks/[id].tsx. Screen của Tabs trở thành tasks, còn Stack bên trong dùng name index và [id]. Đừng giữ đồng thời detail cũ bên ngoài với cùng public URL nếu chưa chủ ý dùng cơ chế shared routes.

Bài 5 Phân biệt dữ liệu và URL

Tạo task 3, sao chép URL detail, Reload app rồi mở lại URL đó. Giải thích vì sao route vẫn khớp nhưng task không tồn tại. Đề xuất lớp cần thêm để sửa yêu cầu lưu dữ liệu.

Xem hướng giải

File dynamic vẫn tồn tại nên Router chọn đúng screen. State Context đã khởi tạo lại nên task 3 biến mất. Muốn dữ liệu bền vững cần lưu và khôi phục từ storage hoặc API; thay navigation API không giải quyết việc mất dữ liệu.

  • Tôi dự đoán được URL từ một file route và ngược lại.
  • Tôi phân biệt route name trong layout với href dùng để điều hướng.
  • Tôi chọn được Stack, Tabs hay Slot theo trải nghiệm cần có.
  • Tôi dự đoán được history sau push, replace và back.
  • Tôi xử lý được params thiếu, sai kiểu và tài nguyên không tồn tại.
  • Tôi biết provider nên sống ở layout nào để chia sẻ state.
  • Tôi đã thử mở thẳng detail/modal bằng deep link.
  • Tôi phân biệt sửa JavaScript, Reload và thay đổi cần native build.
